# 项目深度调研报告（2026-04-24）

## 一、调研范围与方法
- 范围：`src/service_layer`、`src/inference_layer`、`src/data_layer`、`src/core`、`frontend`、`scripts`、部署文件与主文档。
- 方法：基于代码与配置的静态审阅，重点核对“文档描述 vs 实际实现”，并按可用性、稳定性、安全性与可维护性评估。

## 二、项目定位与现状结论
- 该项目是一个“中文钓鱼文本识别与预警系统”，整体采用前后端分离架构。
- 现有可运行主链路已经迁移到 `src/service_layer/app.py`（FastAPI v1 路由组）。
- 仓库同时保留了旧接口栈 `src/api/main.py`，形成“双轨并存”状态，存在维护与使用歧义。
- 当前系统具备检测、样本管理、模型管理、训练任务、系统监控等模块，但部分关键链路存在实现缺陷。

## 三、系统架构（按代码真实实现）

### 1) 前端层
- 技术栈：Vue 3 + Vite + Element Plus + ECharts（见 `frontend/package.json`）。
- 路由：`home`、`single-detection`、`batch-detection`、`alerts`、`performance`、`models`、`training`、`tech-highlights`（见 `frontend/src/router/index.js`）。
- API 封装：集中在 `frontend/src/api/index.js`，统一调用后端 `/api/v1/*`。

### 2) 服务层（FastAPI）
- 入口：`src/service_layer/app.py`。
- 生命周期：启动时初始化数据库、推理服务、资源监控；关闭时停止监控。
- 路由模块：`detection`、`alerts`、`samples`、`models`、`training`、`system`。
- 中间件：CORS 全开放、请求耗时与请求 ID 注入。

### 3) 推理层
- 核心：`src/inference_layer/inference_service.py`、`model_manager.py`、`resource_monitor.py`。
- 能力：模型加载、单条/批量预测、缓存命中、模型重载与激活切换、资源采样。

### 4) 数据层
- ORM：SQLAlchemy + SQLite（`src/data_layer/database.py`）。
- 仓储：`src/data_layer/repository.py`。
- 核心实体：`DetectionRecord`、`AlertInfo`、`SampleData`、`ModelVersion`、`TrainingLog`（`src/data_layer/models.py`）。

## 四、核心业务链路梳理

### 1) 检测链路
- 入口：`POST /api/v1/detection/single|batch|sms|email|link`（`src/service_layer/api/detection.py`）。
- 执行：调用 `InferenceService.predict(...)` 返回预测结果。
- 落库：写入 `detection_records`。
- 现状：检测结果会写库，但“自动预警联动”未在该链路中生效。

### 2) 训练链路
- 入口：`POST /api/v1/training/start`（后台任务）。
- 实现：后台线程执行 `_run_training_task`，通过子进程调用 `src/core/train_bert_textcnn.py`。
- 现状：参数协议不匹配，导致训练任务可能在启动阶段直接失败（详见风险 P0-1）。

### 3) 模型管理链路
- 入口：`/api/v1/models/*`。
- 现状：版本信息既在数据库中管理，也在 `models/model_versions.json` 中管理，存在双来源风险。

## 五、关键问题与风险评估

### P0（高优先级，影响主功能）
1. **训练任务参数不兼容**
   - 位置：`src/service_layer/api/training.py` 与 `src/core/train_bert_textcnn.py`。
   - 现象：API 传 `--epochs/--batch-size/--learning-rate`，训练脚本不接收这些参数。
   - 影响：`/training/start` 任务高概率失败。

2. **场景检测接口实现缺陷**
   - 位置：`src/service_layer/api/detection.py`。
   - 现象：`detect_sms/email/link` 通过 `**kwargs` 转调 `detect_single`，未显式声明依赖注入参数。
   - 影响：运行期可能因参数绑定异常导致接口不可用。

3. **预警自动生成链路未打通**
   - 位置：`src/service_layer/api/alerts.py` 与 `detection.py`。
   - 现象：存在预警创建函数，但检测流程未调用。
   - 影响：系统宣称“自动预警”，但落地行为不完整。

### P1（中高优先级，影响稳定性/安全）
1. **趋势统计实现存在类型错误**
   - 位置：`src/data_layer/repository.py`。
   - 现象：`get_trend_data()` 使用 `Integer`，文件末尾仅导入 `IntegerType`。
   - 影响：`/system/trends` 存在运行期报错风险。

2. **潜在 SSRF 风险**
   - 位置：`src/inference_layer/inference_service.py`（网络特征采集）。
   - 现象：对输入 URL 发起直接请求。
   - 影响：可能被利用进行内网探测或访问受限地址。

3. **CORS 过宽**
   - 位置：`src/service_layer/app.py`。
   - 现象：`allow_origins=["*"]` 且 `allow_credentials=True`。
   - 影响：生产环境安全边界过弱。

### P2（中优先级，影响长期维护）
1. 旧新 API 并存（`src/api/main.py` 与 `src/service_layer`），提高认知成本。
2. 模型版本双数据源（DB + JSON），易出现状态漂移。
3. 文档与代码偏差较大，新增成员上手成本高。

## 六、文档一致性审计
- `README.md` 中存在较多“历史结构/旧入口”描述，与当前运行入口不完全一致。
- 项目说明强调完整自动预警与训练能力，但代码主链路仍有断点。
- 建议将 README 以“当前可运行路径”为唯一标准重写。

## 七、可运维与工程化观察
- 优点：
  - 路由分层与仓储层职责较清晰。
  - 前端 API 封装集中，页面结构完整。
  - 提供了 Docker Compose 编排与启动脚本。
- 短板：
  - 缺少关键链路的端到端自动化验证（训练、场景检测、趋势统计、预警联动）。
  - 对外部 URL 的采集策略缺乏安全防护与降级开关。

## 八、建议整改路线图

### 第 1 阶段（1-2 天，止血）
- 修复训练参数协议：统一 API 与训练脚本入参。
- 修复 `detect_sms/email/link` 依赖注入签名。
- 将“检测结果 -> 预警创建”联动接入主链路。
- 修复 `get_trend_data()` 的类型导入错误并补回归测试。

### 第 2 阶段（3-5 天，稳定）
- 为 URL 采集增加 SSRF 防护（协议白名单、内网地址拦截、超时与重试策略）。
- 收敛生产 CORS 配置为受信任域名。
- 统一模型版本单一事实源（建议保留 DB 或 JSON 之一）。

### 第 3 阶段（1 周，治理）
- 清理或显式标记旧 API 栈为 deprecated。
- 重写 README 与部署文档，补齐“当前架构图 + 实际启动方式 + API 清单”。
- 增补端到端测试与 CI 检查，避免核心能力回归。

## 九、综合结论
- 该项目具备较完整的产品雏形与工程骨架，但目前处于“架构升级过渡期”。
- 若优先修复 P0/P1 问题，系统可从“功能可演示”提升到“功能可稳定交付”。
- 建议先完成主链路闭环（检测-预警-训练-统计）后再开展性能与体验层优化。
